## SWI C01 — Reservation System: Start the Engineering Project

Tým 3–4 studenti · pracovní blok 90 minut · deadline před C02

**Deadline:** před začátkem C02. Nemusíte všechno dokončit během 90 minut
C01. Na cvičení udělejte maximum. Všechny povinné výstupy a celý Definition
of Done musí být hotové před začátkem vašeho C02. C02 předpokládá, že C01
je dokončeno.

**Výsledek C01:** společný repo, jasně vymezený rezervační systém, Project
Frame, jedna review smyčka, jeden skutečně provedený engineering spike,
evidence a definovaný walking skeleton pro CP1.

### Rozsah implementace v C01

V C01 nemusíte implementovat celý reservation system. Operace, stavy a
pravidla níže definují zamýšlený rozsah systému pro další týdny. V C01 musí
být technicky skutečně provedena pouze jedna zvolená engineering spike.

Do C02 tedy musí být:

- celý minimální reservation domain definovaný;
- repo a project skeleton připravený;
- jedna engineering spike skutečně provedena a ověřena;
- CP1 walking skeleton pouze definovaný.

Walking skeleton musí být skutečně runnable až po C03 / před C04.

### 1 Vytvořte tým a repo

- 3–4 studenti.
- Jeden společný repozitář.
- Všichni členové mají přístup.

**Povinný výstup do C02:** název týmu + členové + URL repozitáře.

### 2 Zvolte, co rezervujete

Typ systému je pro všechny stejný: reservation system. Volíte pouze
rezervovaný resource.

Příklady: místnost, laboratorní zařízení, auto, sportoviště, parkovací
místo, nabíjecí stanice, konzultační termín, sdílený nástroj.

| Povinný prvek | Minimum |
|---|---|
| Resource | co se rezervuje |
| Reservation | identita, čas/slot, stav |
| User | kdo rezervaci vytváří |
| States | např. DRAFT / CONFIRMED / CANCELLED |
| Operations | create, confirm/approve, cancel, check availability |
| Common rule | dvě potvrzené rezervace stejného resource se nesmí překrývat |
| Boundary | alespoň jedna dependency; defaultně Notification Service |

Přidejte jedno vlastní domain-specific business rule.

**Povinný výstup do C02:** konkrétní reservation domain + jedno vlastní
business rule.

```

```

Podporovaný stack: např. Java 21 + Spring Boot + Maven + PostgreSQL +
JUnit. Jakýkoliv stack je povolen, ale tým si jej podporuje sám a zdůvodní
své rozhodnutí.

**Povinný výstup do C02:** repo existuje a lze do něj commitovat.

## SWI C01 — Reservation System: Start the Engineering Project (English)

Team of 3–4 students · 90-minute guided work session · deadline before C02

**Deadline:** before the start of C02. You do not have to finish every task
within the 90 minutes of C01. Do as much as possible during the class. All
required outputs and the complete Definition of Done must be finished
before your C02 starts. C02 assumes that C01 is complete.

**C01 result:** a shared repository, a clearly scoped reservation system,
Project Frame, one real review cycle, one executed engineering spike,
evidence, and a defined CP1 walking skeleton.

### 1 Create the team and repository

- 3–4 students.
- One shared repository.
- All team members have access.

**Required before C02:** team name + members + repository URL.

### 2 Choose what your system reserves

The system type is fixed for all teams: reservation system. You choose
only the reserved resource.

Examples: room, laboratory equipment, vehicle, sports facility, parking
place, charging station, consultation slot, shared tool.

| Required element | Minimum |
|---|---|
| Resource | what is reserved |
| Reservation | identity, time/slot, state |
| User | who creates the reservation |
| States | e.g. DRAFT / CONFIRMED / CANCELLED |
| Operations | create, confirm/approve, cancel, check availability |
| Common rule | two confirmed reservations of the same resource must not overlap |
| Boundary | at least one dependency; default: Notification Service |

Add one domain-specific business rule of your own.

**Required before C02:** a concrete reservation domain + one
domain-specific business rule.

### 3 Prepare the repository

```
README.md
docs/
  intent-and-change.md
  architecture-and-decisions.md
  evidence-and-evolution.md
src/  (or equivalent source directory)
```

Supported stack: e.g. Java 21 + Spring Boot + Maven + PostgreSQL + JUnit.
Individual stack is allowed, it is up to the team. Rationale has to be
provided.

**Required before C02:** the repository exists and the team can commit to
it.

### 4 Complete the Project Frame

Put the following structure into `docs/intent-and-change.md` and complete
it:

```
# Project Frame

## Reservation domain
What exactly do we reserve?

## Purpose
2–3 sentences: who the system is for and why it exists.

## Users / Stakeholders
1–3 roles.

## Core concepts
Reservation, Resource, User + optionally 0–3 additional domain concepts.

## Core operations
- Create reservation
- Confirm / approve reservation
- Cancel reservation
- Check availability

## Persistent state
What we store about Reservation and Resource.

## State-changing operation
For example DRAFT → CONFIRMED.

## Common business rule
Confirmed reservations for the same resource must not overlap.

## Domain-specific business rule
One rule specific to your domain.

## External / system boundary
One dependency. Default: Notification Service.

## Assumption
One thing you currently treat as true but are not certain about.

## Unknown
One important thing you do not yet know.
```

**Required before C02:** all Project Frame fields are completed.

### 5 Select one future pressure

| C | Changeability — new state, provider, resource type, or rule. |
| R | Risk / Higher consequence — failure starts to have a much larger impact. |
| L | Release / Operation — config/schema/rollback/incident. |

```
## Selected future pressure
Category: Q / C / R / L
Concrete pressure:
Why it is relevant to our reservation system:
```

**Required before C02:** exactly one concrete pressure + rationale. You do

### 6 Perform one real change + review cycle

- Create an issue/task named C01 engineering spike.
- One team member makes the change.
- Another team member reviews it before integration.
- Integrate the change.

**Required before C02:** one integrated change that was reviewed by
another team member before integration.

### 7 Execute one engineering spike

Choose exactly one:

| Option | Description | Evidence |
|---|---|---|
| A — Persistence | Reservation → real DB → load it again → verify. | running code + test/command |
| B — Boundary failure | Notification Service/stub → success → timeout/failure. | test/script showing both cases |
| C — Reproducible build/config | clean checkout by another team member → build/test/run using only README → fix a discovered obstacle. | README + successful build/run |

Not a valid spike: description only, diagram only, unverified README, or
generated code that nobody executed.

**Required before C02:** one spike was actually executed and its evidence
is in the repository.
