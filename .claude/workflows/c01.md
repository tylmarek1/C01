# Workflow: C01 (engineering-spike kickoff)

**Triggers:** "dokonči C01," starting a fresh team/repository from this
same course structure, or auditing whether C01's Definition of Done is
actually satisfied.

**Current status:** already complete for Courtly. `docs/project-state.md`
records this with evidence pointers (PR #5, `docs/evidence-and-evolution.md`'s
spike section, `docs/intent-and-change.md`'s filled Project Frame, root
`README.md`'s own checked-off DoD table). Re-running this workflow on this
repository today should mean re-*verifying* those gates against
`docs/course/C01.md` §10, not redoing the work. This file is written to
also be directly reusable if this repository's structure is ever copied
for a new team or a future course iteration starting from zero.

## Procedure

1. **Load `docs/course/C01.md`** — the actual assignment, not a
   recollection of it.
2. **Team and repository** (§1) — confirm 3–4 members with repo access;
   record team name + members + URL where the assignment's "required
   output" asks for it (currently root `README.md`'s "Team" section).
3. **Choose the reservation domain** (§2) — pick the resource, and
   confirm the minimum element table is satisfied: Resource, Reservation,
   User, meaningful states, the four operations, the common overlap rule,
   one boundary dependency (default: a Notification Service). Add exactly
   **one** domain-specific business rule — not zero, not several.
4. **Prepare the repository** (§3) — `README.md` and `docs/intent-and-
   change.md`, `docs/architecture-and-decisions.md`,
   `docs/evidence-and-evolution.md` exist; a stack is chosen and its
   rationale is written down (see `docs/architecture-and-decisions.md`
   ADR-000 for the pattern).
5. **Fill the Project Frame** (§4) — every field in
   `docs/intent-and-change.md`, using the exact template from
   `docs/course/C01.md` §4. An empty or placeholder field is not
   "filled."
6. **Select exactly one future pressure** (§5, Q/C/R/L) — a concrete
   pressure and why it's relevant, written into the Project Frame. Do not
   implement it in C01 — selecting and justifying it is the whole
   requirement.
7. **Run one real change + review cycle** (§6) — an issue/task for "C01
   engineering spike," one member makes the change, a *different* member
   reviews it before it's integrated. The review must have actually
   happened, not be asserted after the fact — a PR with a real approving
   review from a non-author is the evidence (see `docs/project-state.md`'s
   own pointer to PR #5 for the pattern).
8. **Execute exactly one engineering spike** (§7) — pick variant A
   (persistence), B (boundary failure), or C (reproducible build). It must
   be *executed*, not described: running code plus a test/command
   (A/B) or a successful clean-checkout build (C). A diagram or an
   unverified README does not count.
9. **Record evidence and decision** (§8) — into
   `docs/evidence-and-evolution.md`, using the exact four-field template
   from `docs/course/C01.md` §8 (question/unknown, what we did, observed
   result, decision). All four fields concrete, not placeholders.
10. **Define the CP1 walking skeleton** (§9) — one end-to-end path in
    `README.md`, in the exact shape the assignment gives
    (`POST /reservations → validate → persist → return id → automated
    check`). It only needs to be *defined* here, not fully implemented —
    don't over-build this step.
11. **Gate check** — walk all 15 items of `docs/course/C01.md` §10
    explicitly, record each DONE-with-evidence or NOT-DONE, per
    `docs/definition-of-done.md`. Update `docs/project-state.md`.
